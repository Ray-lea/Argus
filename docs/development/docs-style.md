# 文档规范

本页规定仓库文档的分类、页面结构、行文、格式与检查方法，适用于 `docs/` 下的全部页面，以及根目录和 `.github/` 中面向公众的 Markdown 文件。修改或新增文档前先阅读本页；提交前运行 `pnpm docs:lint` 检查。

规范参考 Diátaxis、Google 开发者文档风格指南、Microsoft 写作风格指南、《中文技术文档的写作规范》、《中文文案排版指北》与 ASD-STE100，来源见[参考资料](#参考资料)。这些来源与本项目的情况不一致时，按本项目取舍：文档以简体中文书写，同时在 GitHub 和[官网](website.md)上渲染。

## 适用范围与读者

不同文件面向不同读者，内容不互相混写。

| 文件 | 读者 | 内容 |
| --- | --- | --- |
| `README.md` 及其他语言版本 | 首次了解项目的用户 | 简介、特性、系统要求、构建入口、文档入口 |
| `docs/start/` | 初次使用的用户 | 什么是 Argus、快速入门、安装与更新、与其他工具的对比 |
| `docs/guide/` | Argus 的用户 | 界面、操作、设置与数据口径 |
| `docs/development/` | 贡献者与维护者 | 开发环境、命令、构建、测试、发布 |
| `docs/architecture/`、`docs/design/` | 贡献者 | 模块职责、数据流、设计取舍及其依据 |
| `AGENTS.md`（根目录与各子目录） | AI 代理 | 代理的工作规则与经验 |
| `changelog/` | 用户 | 各版本的变化，写法见[更新日志的内容](release.md#更新日志的内容) |

`docs/` 只写给人看的内容。约束 AI 代理行为的规则写进对应目录的 `AGENTS.md`，例如征得同意的范围、回复中要说明的事项和代理工具的用法。面向人的说明不能只写在 `AGENTS.md` 里。

## 文档类型

文档按 Diátaxis 分为四类，每类回答读者的一种需要。

| 类型 | 读者的需要 | 写法 |
| --- | --- | --- |
| 教程 | 第一次上手，边做边学 | 一条完整的路线，每步都有可见的结果 |
| 操作指南 | 完成一项具体任务 | 以目标为标题，按顺序写出步骤 |
| 参考 | 查阅准确的事实 | 按产品结构组织，用表格和列表列出条目 |
| 说明 | 理解原因与原理 | 讲清背景、机制、取舍与依据 |

判断一段内容的类型，先问两个问题：读者是在操作还是在理解，是在学习还是在工作。操作且学习是教程，操作且工作是操作指南，理解且工作是参考，理解且学习是说明。

一个页面以一种类型为主，一个章节只写一种类型。参考页中插入的原理说明移到说明类章节或页面；操作步骤中的背景知识只保留完成操作所需的一句，其余链接到说明。

`docs/README.md` 是全部文档的索引；每个子目录的 `README.md` 是该部分的入口页，链接本目录下的其他页面。各目录的主要类型如下：

- `start/`：教程与说明。快速入门是全库唯一的教程，从安装到完成第一项操作；其余页面介绍 Argus 是什么、如何安装，以及与其他工具的区别。
- `guide/`：参考与操作指南，按界面的页面组织；统计口径与数据来源等说明单独成页。
- `development/`：操作指南与参考，按任务组织，命令与变量用表格列出。
- `architecture/`：说明，按模块组织，写职责、数据流和边界。
- `design/`：说明，写设计决策、实测依据与被否决的方案。

不必为凑齐四种类型而新建页面或空的章节。结构随内容增加而调整，确有一条完整的上手路线时再写教程。

## 页面结构

每个页面以一级标题开头，下一段是导语。导语用一两句说明本页的内容与读者，不超过 150 字；官网把它用作页面摘要和搜索结果的说明。导语之前不放表格、列表或告警块。

标题的写法：

- 每页只有一个一级标题。章节从二级标题开始，逐级使用，不跳级，最多到四级。
- 操作指南的标题用动宾结构，例如“导出当前页为 CSV”；参考与说明的标题用名词短语，例如“内存统计口径”。
- 标题不加标点，不编号，不放链接，不用加粗或代码格式包住整个标题。下级标题不重复上级标题的名称。
- 同一级的标题至少两个，只有一个下级标题时不分级。上级标题与下级标题之间先写一段正文，不叠放标题。
- 同一页内的标题不重名。被其他文件链接的标题改名或移动时，同时更新所有链接；外部已发布的链接（更新日志、README）指向的标题保留原名。

页面的文件名用小写英文单词，单词之间用连字符连接，例如 `hardware-data.md`。

每个章节围绕一个主题。同一标题下的段落、列表、表格与代码块合计超过 8 个时，按主题拆分出下一级标题。一个页面超过约 15,000 字时，按页面、任务或模块拆分成多个页面。

新增、移动或拆分页面时，同时更新所在目录的 `README.md`、`docs/README.md` 和根目录 `README.md` 中受影响的链接。

官网按 `docs/README.md` 生成侧栏：一个分组的页面同在 `docs/` 的一个子目录中时，该分组显示为可展开的文件夹，页面顺序与索引一致。新页面的侧栏图标在 `website/scripts/content.mjs` 的 `pageIcons` 中登记。

## 段落与句子

一个段落只讲一个主题，第一句是主题句，后面的句子补充依据、条件或例外。段落之间空一行，段首不留空格。

段落宜在 150 字以内，不超过 250 字，句数不超过 6 句。内容较多时拆成几段，或把并列的条目改为列表、把同类属性的比较改为表格。

句子的写法：

- 一句只说一件事。说明性句子宜在 50 字以内；操作步骤宜在 35 字以内。
- 用主动语态和陈述语气，直接写结论、事实与操作。不用双重否定，少用“被”字句。
- 代词的指代要明确。“它”“该”“此”指代的对象不唯一时，重复名称。
- 条件放在动作之前：先写“需要……时”“……之后”，再写要执行的操作。
- 不重复限定，不先否定再转折。影响操作、安全或数据解释的条件，紧贴对应内容写一次。

## 语气与用词

文档使用书面语。下列写法不用：

- 第二人称“你”“您”和第一人称“我们”。需要指称读者时用“用户”，或省略主语。
- 口语与模糊的说法，例如“搞定”“挺”“其实”“基本上”“几乎瞬间”“连不上”。改用“完成”“较”“可”“仅”“暂无”等说法。
- 无法核实的形容，例如“非常快”“很稳定”。用实测数字代替，并注明条件。

术语与界面文案保持一致：界面上的名称以 `locales/zh-CN` 的文案为准，固定缩写、单位与常用界面术语见[多语言的术语表](i18n.md#术语表)。同一概念在全库只用一种说法。

实测数字注明机器、构建类型与刷新间隔等条件。推翻旧结论时直接改正文，不保留错误的说法。文档不写验收清单、逐轮测试记录或“待验证”之类的状态，测量原始记录留在构建产物目录。

## 列表

列表用于两项及以上的并列内容，宜不超过 7 项；项数更多时分组，或改用表格：

- 无序列表用于没有先后之分的条目，项目符号统一用 `-`。
- 有序列表用于操作步骤，或有先后、优先级的条目，编号写成 `1.`、`2.`、`3.`。

列表前用一句引导语说明列表的内容，以冒号结尾。同一列表的各项结构平行：都是名词短语，或都是完整的句子。完整的句子以句号结尾，短语不加标点。

每项只写一个要点，宜在 100 字以内，不超过 200 字。列表最多嵌套两层；第二层仍然很长时，改为下一级标题。

条目由名称和说明组成时，写成定义列表：名称加粗，后接全角冒号。

```markdown
- **健康状况**：状态、剩余寿命、温度与可用备用空间。
- **设备信息**：型号、固件版本、序列号与容量。
```

操作步骤的写法：

- 每步一个动作，以动词开头；同一位置的几个短动作可以合为一步。先写位置，再写动作，例如 `在**设置 → 更新**中，单击**检查更新**`。
- 操作的目的写在动作之前，结果写在同一步的下一句，或写在列表之后。
- 前提条件写在步骤之前。可选的步骤以“可选：”开头。步骤超过 9 步时，按阶段拆成几组。
- 只有一个步骤时写成一个段落，不用列表。

## 表格

表格用于多个条目在相同属性上的比较或查阅，至少 3 行，宜为 2–5 列。只有两项内容或每项只有一个属性时，用段落或列表。

表格前用一句话说明表格的内容。首列放条目的名称，表头用简短的名词。

单元格只写短语或一句话，宜在 40 字以内，不超过 80 字。单元格中不放列表、多个段落、代码块和 `<br>` 换行。某一项需要较长的说明时，表格中只写摘要，在表格后另起段落或小节说明，并从单元格链接过去。

单元格不留空，没有内容时写“无”。不在编号的操作步骤之间插入表格。

## 告警块

提示、警告与破坏性操作的风险用告警块，不藏在正文的括号里。告警块使用 GitHub 的语法，官网渲染为带标题的提示框：

```markdown
> [!CAUTION]
> 不要在开发机上设置 `ARGUS_DISPOSABLE_MACHINE=1`：设置后，安装与卸载测试会改动这台机器。
```

五种类型按严重程度由低到高排列，用法如下：

| 语法 | 官网标题 | 用途 |
| --- | --- | --- |
| `[!NOTE]` | 说明 | 略读时也应知道的补充信息 |
| `[!TIP]` | 提示 | 可选的、更省事或效果更好的做法 |
| `[!IMPORTANT]` | 重要 | 完成操作必须满足的条件或必须知道的限制 |
| `[!WARNING]` | 警告 | 需要立即注意、以免出现问题的情况 |
| `[!CAUTION]` | 危险 | 会删除数据、改动系统、带来安全风险或无法撤销的操作 |

告警块的写法：

- 放在它所约束的步骤或段落之前，内容不超过 3 句：先写要做或不要做的事，再写原因。
- 少用告警块：能写进正文的内容写进正文，一节宜不超过一个。正文的主要内容不放进告警块。
- `[!NOTE]` 只提供信息，不写操作指令。
- 两个告警块不相邻，不嵌套，告警块中不放标题。
- 不使用普通引用块。引用原文时改用正文转述，并给出来源链接。

## 格式语义

每种 Markdown 格式在全库只表示一类内容，见下表。

| 内容 | 格式 | 示例 |
| --- | --- | --- |
| 命令、文件名、路径、配置键、环境变量、命令行参数、注册表路径、代码标识、进程映像名、需要输入的值 | 行内代码 | `pnpm docs:lint`、`resources/app.json`、`explorer.exe` |
| 界面元素：页面、按钮、菜单、选项卡、设置项、选项、对话框、列名 | 加粗 | 单击**运行新任务** |
| 界面路径 | 加粗，层级之间用“ → ” | **设置 → 权限 → 特权服务** |
| 界面上显示的文字：状态、提示、通知、错误信息 | 中文引号 | 状态栏显示“已暂停刷新” |
| 定义列表的条目名称 | 加粗，后接全角冒号 | **健康状况**：状态与剩余寿命 |
| 按键与组合键 | 正文，键名之间用 `+` 连接，不加空格 | Ctrl+Shift+Esc |
| 命令中的占位符 | 尖括号，写在代码内 | `node scripts/ui-shots.mjs <标签> <步骤文件>` |

格式的限制：

- 加粗只用于界面元素和定义列表的条目名称，不用于强调。需要强调的内容改写句子，或改用告警块。
- 不使用斜体，不用代码格式表示强调。
- 界面路径写完整的层级，整条路径放在一对加粗标记内。
- 引用界面元素时，去掉标签末尾的冒号与省略号，例如界面上的“运行新任务…”写作**运行新任务**。名称后不必加“按钮”“菜单”等词，需要区分时再加。
- 加粗标记与相邻的汉字之间不加空格，例如 `在**关于**页单击**复制诊断信息**`。加粗的内容是英文或数字时，按中英文混排的规则在标记外侧加空格，例如 `选择 **Check**，再运行`。
- 加粗的内容以标点开头或结尾、并且紧邻汉字时，GitHub 与官网都不会把它解析为加粗。调整句子，使加粗标记外侧是空格、标点或句子边界。

## 中英文排版

中英文混排遵循《中文文案排版指北》：

- 汉字与英文字母、数字之间加一个空格，例如“使用 Windows 11 的 Mica 背景”。
- 数字与单位之间加空格，例如“8 px”“100 KB/s”；百分号和度数不加空格，例如“15%”“90°”。
- 全角标点与英文、数字之间不加空格。
- 中文语境使用全角标点；完整的英文句子、代码与专有名词内使用半角标点。
- 数值范围用短横线“–”连接，例如“150–320 px”。超过 4 位的整数用逗号分隔千位，例如“10,000”。
- 引号使用“”，引号内再引用时用‘’，不用直角引号。
- 不重复使用标点。正文中的省略号写作“……”，不与“等”连用。
- 专有名词使用官方的大小写，例如 GitHub、PowerShell、NVMe、Windows；不使用不规范的缩写。

## 代码块与命令

代码块标注语言：Windows 命令用 `powershell` 或 `bat`，只能在 Bash 中运行的命令用 `bash`，输出与纯文本用 `text`，配置按文件类型标注 `json`、`jsonc`、`toml` 等。

命令块的写法：

- 一行一条命令，不写提示符。
- 需要说明用途时，在行尾或上一行加注释。
- 占位符用尖括号，并在代码块前后说明它的取值。
- 只读或会改动机器的命令写在不同的代码块中，会改动机器的命令之前加告警块。

## 链接与图片

仓库内的页面用相对路径链接，指向 `.md` 文件和章节锚点，例如 `[更新](settings.md#更新)`。外部链接使用 `https://`。

链接文字写目标页面或章节的名称，不写“这里”“此处”“链接”。同一段中指向同一目标的链接只保留第一个。

图片放在 `docs/images/`，提供描述画面内容的替代文字。截图按深浅两种主题分别提供时，文件名以 `-light`、`-dark` 结尾。

## 随代码更新

代码的行为变化时，在同一提交中更新对应的页面，例如快捷键、设置项、默认值、模块职责与 IPC 命令。根目录 README 的特性列表与快捷键表只放最常用的内容，完整说明写在 `docs/`。

## 检查工具

`pnpm docs:lint` 检查 Markdown 的结构、本规范中可以自动判断的写法、中英文排版与仓库内的链接；给出文件路径时只检查这些文件。`pnpm check`、`pnpm verify` 和拉取请求的检查都会运行它。

| 检查 | 工具 | 内容 |
| --- | --- | --- |
| Markdown 结构 | markdownlint-cli2 | 标题层级、列表符号、代码块语言、空行与表格格式 |
| 篇幅与格式语义 | 仓库自定义规则 | 段落、句子、列表项与单元格的长度，告警块语法，加粗与界面路径 |
| 用词 | 仓库自定义规则 | 第二人称、口语与给代理的说明 |
| 链接 | 仓库自定义规则 | 仓库内的文件与锚点是否存在，含其他文件指向 `docs/` 的锚点 |
| 中英文排版 | AutoCorrect | 空格、全角与半角标点、专有名词的大小写 |
| 外部链接 | lychee | 每晚检查一次外部网址是否失效 |

`pnpm docs:lint --fix` 自动修正 markdownlint 与 AutoCorrect 能修正的问题，其余问题按提示修改。规则配置在根目录的 `.markdownlint-cli2.jsonc`、`.autocorrectrc` 与 `lychee.toml`，自定义规则在 `scripts/lib/docs-lint/`。AutoCorrect 没有 ARM64 版本，在 ARM64 电脑上运行时跳过这一项。

确实需要例外时，用注释关闭一条规则，并写明原因。段落、列表与标题可以只关闭下一行：

```markdown
<!-- markdownlint-disable-next-line argus-sentence-length -- 引用的原文不能拆分 -->
```

表格须在整张表的前后成对关闭与恢复，写在表格行之间的注释会截断表格：

```markdown
<!-- markdownlint-disable argus-table-cell-length -- 原始值的完整定义 -->
| 属性 | 定义 |
| --- | --- |
<!-- markdownlint-enable argus-table-cell-length -->
```

## 取舍说明

参考的规范之间有不一致之处，也有不适用于中文的条款。本项目的取舍如下：

| 事项 | 参考规范的做法 | 本项目 |
| --- | --- | --- |
| 人称 | Google 与 Microsoft 用第二人称和对话式语气 | 不用“你”“您”，省略主语或用“用户” |
| 引号 | 《中文文案排版指北》建议直角引号 | 用“”，与界面文案和《中文技术文档的写作规范》一致 |
| 界面路径 | Google 整条加粗并用“>”；Microsoft 用“>”且不加粗 | 整条加粗，层级之间用“ → ” |
| 按键 | Google 用 `<kbd>` 标记；Microsoft 在操作说明中加粗 | 正文，不加格式 |
| 提示框 | Google 定义四类；Microsoft Learn 与 GitHub 定义五类 | 采用 GitHub 的五类语法 |
| 句子长度 | ASD-STE100 按英文词数限制：步骤 20 词，说明 25 词 | 按字数：步骤宜 35 字以内，说明宜 50 字以内，检查上限 120 字 |
| 文档体系 | 《中文技术文档的写作规范》按入门、进阶分篇 | 按 Diátaxis 的读者需要分类 |

ASD-STE100 的核准词表、名词串长度与禁用分号等条款针对英文，不适用于中文；本项目采用其中一步一个指令、条件在前、一段一个主题、一个概念一个术语与警告先写指令的原则。

- [Google developer documentation style guide](https://developers.google.com/style)：[文本格式](https://developers.google.com/style/text-formatting)、列表、表格、操作步骤与提示框。
- [Microsoft Writing Style Guide](https://learn.microsoft.com/style-guide/welcome/)：界面元素与按键的格式、操作步骤与易于扫读的内容。
- [Microsoft Learn 的告警语法](https://learn.microsoft.com/contribute/content/markdown-reference)：五种告警块的用途与数量建议。
- [中文技术文档的写作规范](https://github.com/ruanyf/document-style-guide)：标题、段落、句子、数值与标点。
- [中文文案排版指北](https://github.com/sparanoid/chinese-copywriting-guidelines)：中英文混排的空格、标点与专有名词。
- [ASD-STE100 Simplified Technical English](https://www.asd-ste100.org/)：一步一个指令、条件在前、主动语态与警告的写法。
- [GitHub 的告警语法](https://docs.github.com/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#alerts)：告警块的写法与渲染。
