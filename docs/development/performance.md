# 性能测量

测量使用发行构建、独立应用标识与相同数据源，记录窗口客户区物理尺寸、DPI、刷新间隔、曲线模式、设备、主题和实际呈现帧率。CPU 与 GPU 比较需要相同的实际画面和节拍；设置的 FPS 不等于实际 FPS。

tools/window-probe 通过 Job 跟踪测试进程，采样累计 CPU 时间、内存及 GPU 引擎时间，通过 Windows.Graphics.Capture 观察目标窗口的呈现间隔。DWM 服务整个桌面，其消耗不能全部归因于 Argus。忙碌开发机上的进程占用结果需要多轮交替与稳定性判断。

应用以 --hidden --test --identifier <独立标识> 启动；工具使用 HWND_BOTTOM 和 NOACTIVATE 显示，并每 50 ms 监视前台。截图与帧统计只捕获该窗口，隐藏窗口的回调不能替代实际呈现统计。测试完退出实例并清理自身测试数据。

这样显示的测试窗口不在前台，Windows 可能对其进程启用 EcoQoS（功耗限制），在混合架构处理器上把线程放到能效核并降低调度优先级。机器繁忙（例如并行编译）时，界面线程上的耗时因此会放大数十倍：同一次切换页面，测得的单帧绘制从约 50 ms 变为 1.3 s。在繁忙的机器上测量界面线程耗时，应关闭测试进程的功耗限制（`SetProcessInformation` 的 `ProcessPowerThrottling`），必要时提高其优先级并限定在性能核上，使其接近用户操作的前台窗口；结果仍需交替测量，并注明当时的负载。

渲染变更关注长帧分布、连续更新时的路径构建次数、可见和隐藏状态开销。静态文字或布局修正不需要重复完整性能对照。详细原始结果留在 target，不作为跨技术栈通用基线。

`node scripts/perf-native.mjs <标签> <EXE路径>` 预热 25 秒后依次测量进程页、CPU 总览、多核、静态设置页和隐藏状态；`--seconds` 设置每段时长，`--phases` 可指定页面与曲线模式。CPU 汇总所属 Job 中的进程，GPU 按物理适配器与引擎合并所属进程的运行时间，DWM 单独记录。内存同时记录私有提交量与工作集。结果中的实际呈现间隔来自窗口捕获，不能以动画回调计数代替。

对照 Tauri 时添加 `--tauri --identifier <编译时的测试标识>`；必须先使用独立标识构建测试 EXE。该模式仅为所属测试实例打开本地 CDP 端口，禁用遮挡节流，并在退出时关闭实例。`--probe` 可指定探针路径。测量期间不执行构建或截图，交替运行多个样本，并核对分辨率、图表模式和实际帧率。

定位帧率损失时，可设置 `ARGUS_GPUI_FRAME_TRACE=1`，记录显示同步、绘制、提交、纹理上传和文字排版的时间点，以及完整绘制各阶段耗时。该记录不包含界面内容。`ARGUS_GPUI_VIEW_TRACE=1` 另外启用详细视图分析，其自身开销较大，仅用于定位调用路径，不能代替关闭分析器后的 A/B。提交次数也不能替代窗口捕获：显示队列可能舍弃已经提交的帧。

`gpu-frame-trace` 的记录格式为 `[阶段, QPC 时间（100 ns）, 附加值]`。阶段 0 表示同步信号，1/2 表示绘制请求开始/结束，3/4 表示提交开始/结束，6 表示编码开始，10/11 表示纹理上传，12/13 表示文字排版。同步记录的附加值为等待微秒数乘二，最低位表示是否使用休眠回退；`frame-phases` 单独给出完整绘制的各阶段微秒数。

`frame-phases` 另含绘制结束时的性能计数器时间（`atQpc`，100 ns，与窗口捕获同一时钟）、视图 `render` 调用的总耗时（`renderUs`）、重放的缓存视图数（`reused`）、本帧重新渲染的视图（`rendered`），以及各视图在各阶段自身的耗时（`views`）；`frame-present` 记录每次提交的时刻与耗时。界面线程上绘制之外超过 0.3 ms 的工作（命令结果、采样处理、测试控制、行重建等）记为 `ui-work-slice`。`chart-raster` 记录每次曲线纹理的物理尺寸、绘制线程数与耗时，`chart-wait` 记录首次显示的图表在绘制阶段等待纹理的时间及纹理是否在这一帧之前完成。按 `atQpc` 可将这些记录与窗口捕获的呈现时刻对齐，区分慢在绘制的哪一阶段、哪个视图，还是绘制之外。

`layout-work` 记录该帧布局节点数、根布局次数、测量回调次数，以及布局计算、测量、边界查询和清理耗时。测量耗时包含在布局计算内，不能将两者相加。探针按完整行转发应用诊断，避免与帧样本交错；出现无法解析的结构化记录时，测量脚本保留原始输出并判定失败，不将缺失的样本当作长帧。

测量标记记录与窗口捕获同源的 QPC 时间戳，并收集尚未发送的帧批次。`measurementVersion: 2` 按帧自身时间筛选区间，避免 500 毫秒批次跨过边界；布局检查放在计时前的稳定等待内。旧版按批次接收时间划段的结果不与新版合并求平均。

`measurementVersion: 3` 还会核对实际客户区和渲染器视口。自绘标题栏可能在首次调整大小时改变非客户区边距，探针会根据返回尺寸继续校准；脚本同时核对原生布局或 WebView 视口的物理尺寸，任何不匹配都会拒绝该次测量。仅记录请求尺寸的旧结果不能作为等尺寸对照。

探针的 WinRT 多线程环境贯穿整个进程，退出时先停止捕获、注销回调，再关闭测试窗口。`--capture-cycles 50` 可在测量前反复启停捕获，检查捕获对象的清理与重建；正式 A/B 不启用该选项。

`uiThreadCpuMsPerSecond` 记录所属窗口线程的累计 CPU 时间，可用于同一宿主优化前后的定位；Tauri 的宿主窗口线程不包含 WebView 渲染线程，不能将两者直接当成完整渲染开销比较。整应用 CPU 仍使用所属 Job 的汇总值。`missedRefreshes` 根据实际捕获间隔估算缺失的刷新周期，同时保留最长间隔与帧率。

同一 EXE 的诊断对照可设置 `ARGUS_GPUI_DISABLE_PREFIX_COMPOSITION=1`，关闭曲线背景合成，其他绘制参数保持不变。这些开关仅用于定位；正式跨版本对照应记录开关状态，并使用默认配置。

`node scripts/ui-smoke.mjs <标签> --retained --executable <EXE路径> --probe <探针路径>` 使用固定快照，在进程页、CPU 总览与多核页推进动画时间，逐像素比较局部更新与完整重绘。探针需启用 `capture` 功能。普通模拟快照检查覆盖页面、主题、语言、排序和布局；`--live --fluid --move --exercise-updates` 检查持续采样、悬停、窗口移动、缩放与隐藏恢复。
